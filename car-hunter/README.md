# car-hunter

엔카(encar.com) 중고 전기차 매물에서 **이유 없이 싼 차**를 찾는 개인 검토용 도구.
헤이딜러 '숨은이력찾기' 결과를 병합해 최종 순위를 낸다.

**이 도구가 답하려는 질문은 "예산 안에서 뭘 살까" 가 아니다.**
1.5억짜리가 1억에 나오면 예산을 넘겨서라도 사는 것이 목적이므로,
가격으로 거르지 않는다. 대신 이렇게 묻는다:

> 이 차가 시세보다 싸다. **그럴 만한 이유가 있는가, 없는가?**

이유가 있으면(사고·과주행·성능기록부 사진뿐·딜러 장기보유 등) 그건 기회가
아니라 정당한 할인이다. 이유를 못 찾았을 때만 진짜 기회다.

**대상 차종**
- BMW iX 전 트림 (2021~2026년식)
- 벤츠 EQE SUV 전 트림 (2022~2026년식)

대상 차종·연식·점수 가중치는 전부 `config.py` 에서 바꾼다.
차종을 추가하는 방법은 [새 차종 추가하기](#새-차종-추가하기) 참고.

## 매주 한 번 돌리기

```
run_weekly.bat        ← 더블클릭
```

수집 → 채점 → 리포트까지 한 번에 돈다(20~40분). 끝나면 `report.html` 이
자동으로 열린다. 리포트 맨 위에 **지난 실행 이후 달라진 것**(새 매물 /
가격 내린 매물 / 사라진 매물)이 먼저 나온다.

매 실행은 `data/history/YYYY-MM-DD/` 에 통째로 보관되므로, 몇 주 쌓이면
시세가 오르는 중인지 내리는 중인지도 함께 보여준다.

## 데이터 소스의 역할 분담

| 소스 | 담당 | 신뢰도 |
|---|---|---|
| **엔카** | 가격, 연식, 주행거리, 지역, 신차가, 사고 유무, 엔카진단, 소유자 변경 | 객관적 |
| **헤이딜러 숨은이력** | 에어서스 장착, 배터리 제조사, 보험 수리이력 | 출고 기록 기반 |
| ~~엔카 옵션 목록·판매자 설명~~ | **점수에 쓰지 않음** | 딜러 작성 문구 |

엔카의 옵션 목록과 판매자 설명글은 딜러가 홍보용으로 쓴 자유 텍스트다.
없는데 적어두거나 있는데 안 적는 경우가 흔하다. 실제 검증에서 옵션 코드에
없어 "에어서스 미장착" 으로 본 매물의 판매자 설명에 "에어서스펜션, 후륜조향
옵션적용차량" 이 적혀 있었다. 그래서 **에어서스와 배터리 제조사는 1차
점수에 넣지 않고, 3단계 헤이딜러 출고 기록에서 확정한다.** 엔카 쪽 언급
여부는 참고 표시로만 남는다.

## 전체 흐름

```
collect.py  ─→  data/listings.csv , data/details.json
                data/history/YYYY-MM-DD/   (매 실행 보관)
score.py    ─→  data/scored.csv  , report.html (1차)
                  ↓  '설명되지 않는 저평가' 매물의 차량번호를 헤이딜러 앱에서 조회
                  ↓  결과 스크린샷을 hidden/ 에 저장
merge.py    ─→  data/merged.csv  , report.html (최종)
```

세 단계는 서로 독립적으로 실행할 수 있다. 각 단계는 파일로만 소통한다.
`run_weekly.bat` 은 앞의 두 단계를 묶어 한 번에 돌린다.

## 1단계 — 수집 (`collect.py`)

**파서를 믿기 전에 실제 응답부터 확인할 것.**

```bash
python collect.py --probe
```

`--probe` 는 11가지를 실제로 두들겨 보고 결과를 보고한다:

1. `/premium` · `/general` 중 어느 엔드포인트가 살아 있는지
2. 실제 요청 URL (브라우저 주소창에 붙여넣어 대조 가능)
3. 응답 최상위 구조
4. 결과 1건의 전체 필드
5. 필드 매핑 결과 — 실패한 필드에 `<-- 매핑 실패` 표시
   (`trim_detail` 처럼 없어도 정상인 항목은 `(선택 항목)` 으로 구분)
6. **어떤 조건이 매물을 걸러내는지** — 연식 / Hidden / CarType / AdType /
   하위 Model 을 하나씩 빼며 총건수를 비교하고, `CarType` 반대값도 시험한다
7. **연식 필터가 실제로 먹는지** (필터 유/무 총건수와 반환 연식 범위 비교)
8. **페이징이 실제로 먹는지** (1·2페이지 ID 중복 여부)
9. 첫 매물의 **상세 API 4종** (차량번호/옵션, 사고이력, 성능점검, 엔카진단)
10. **옵션 배열 탐색** — 상세 응답 안의 모든 배열을 경로·길이·타입·샘플과
    함께 나열하고, 옵션명 배열 / 옵션 코드 배열 / 코드→이름 변환표를 구분해
    표시한다. 상세 응답 전체는 `data/raw_detail.json` 에 저장된다
11. 최종 파싱 결과 (차량번호, 옵션 수, 에어서스 판별 상태 등)

### 시도했다가 폐기한 방법

`options.etc` 에 딜러가 한글로 적어 둔 항목을 정답 라벨 삼아 옵션 코드의
정체를 역추적하는 스크립트를 만들었으나 **실전에서 틀렸다.** 라벨 자체가
딜러 자유 기술이라 정답이 될 수 없었고, 양성 표본도 1대뿐이라 통계적
근거가 없었다. `samples/experimental_infer_options.py` 에 기록으로만 남겼다.
사용하지 말 것.

## 2단계 — 적정가 산출 (`score.py`)

```bash
python score.py            # 기본 상위 10대
python score.py --top 15
```

**"싼 매물" 이 아니라 "흠결까지 계산에 넣었을 때 값이 합당한 매물" 을 찾는다.**
흠결을 감점이 아니라 **금액**으로 환산해 적정가를 만들고 판매가와 비교한다.

```
적정가 = 기준 시세(동일 연식 · 평균주행)
       - 과주행 할인
       - 사고이력 할인
       - 배터리 보증 잔여 부족 할인
       - 소유자 변경 / 용도 이력 할인
       - 옵션 미장착 할인 (3단계에서 확정)

판단  = 적정가 - 판매가      (플러스 = 저평가, 마이너스 = 고평가)
```

리포트와 콘솔에 항목별 금액이 펼쳐진다:

```
기준 시세 (동일 연식 · 평균주행 66,900km)          6,416
과주행 +1.1만km                                -256
사고이력 내차 1건 · 수리비 269만원 · 외판 1랭크        -269
배터리 보증 잔여 부족 (44% · 기준 50%)              -16
= 적정가                                       5,873
판매가                                         5,800
-> +73만원 저평가 (기회)
```

**흠결이 있어도 그만큼 싸면 위로 올라온다.** 사고차를 무조건 배제하지 않는다.
실제로 무사고 6,100만원 매물(+43만원)보다 사고이력 있는 5,200만원 매물
(+673만원)이 위에 온다.

### 환산 계수 (`config.PRICING`)

| 항목 | 기준 |
|---|---|
| 과주행 | 회귀식의 km 계수를 그대로 사용 (`expected_annual_km` 초과분) |
| 사고 외판 1랭크 | 차값의 1~2% |
| 사고 외판 2랭크 | 3~5% |
| 사고 골격 A랭크 | 8~12% |
| 사고 골격 B랭크 | 15~20% |
| 사고 골격 C랭크 | 25% 이상 (제외 대상) |
| 수리비 | 수리비(만원) × `accident_cost_multiplier` |
| 배터리 보증 | 기준(50%) 미달분을 개월수로 환산 × `manwon_per_month` |
| 소유자 변경 | 1회 초과분당 1% |
| 과거 대여·영업용 | 8% |
| 현재 리스·렌트 | 3% |
| 보험이력 미확보 | 2% (보수적 반영) |

등급 기반과 수리비 기반은 **둘 중 큰 값**을 쓴다(`accident_combine: "max"`).
같은 손상을 두 번 깎지 않기 위해서다. `"sum"` 으로 바꿀 수 있다.
`X`(교환)와 `W`(판금·용접)는 등급 범위 안에서 위치가 갈린다.

3단계 계수는 `config.HIDDEN_PRICING` 에 있다 — 에어서스 미장착 −250만원,
삼성SDI +150만원, 파라시스 −600만원 등.

### 기준 시세를 무사고 매물로 그린다 (`config.BASELINE`)

전체 매물로 회귀선을 그리면 그 선에 이미 사고차의 가격 하락이 섞여 있다.
거기서 사고 할인을 또 빼면 같은 흠결을 두 번 반영하는 셈이다.

그래서 **무사고 매물만으로 기준선을 그린다.** 무사고 표본이
`min_clean_samples`(기본 8) 미만이면 전체 기준선을 쓰되 사고 할인 계수를
`accident_scale_when_all`(기본 0.6)로 낮춘다.

```
mode: "auto"          무사고 표본이 충분하면 무사고, 아니면 전체 (기본)
      "accident_free" 항상 무사고 기준선
      "all"           항상 전체 기준선
```

어느 쪽을 썼는지 콘솔과 리포트에 표시된다:

```
기준선    무사고 매물 기준 (무사고 8대 / 전체 16대, 사고 할인 계수 x1.0)
기준선    전체 매물 기준 (무사고 3대 / 전체 13대, 사고 할인 계수 x0.6)
```

### 이 금액은 상대 비교용이다

계수는 추정치다. 절대 금액이 아니라 매물 간 순위를 가르는 용도로 쓸 것.
기준 시세 자체가 사고차를 포함한 시장 평균이므로, 사고 할인을 다시 빼면
같은 흠결을 일부 중복해 반영하는 셈이다. 리포트에도 이 안내가 들어간다.

### 금액으로 환산할 수 없는 리스크는 제외한다

침수·전손, 골격 C랭크(대시패널·플로어패널), 배터리팩 손상, 주행거리 조작은
할인으로 상쇄할 수 없는 리스크라 후보에서 뺀다. 시세 회귀 표본으로는 계속 쓴다.

### 없는 값은 0 으로 채우지 않는다

응답에 없는 필드는 빈 값으로 두고 리포트에 "응답에 없음" 으로 표시한다.
키는 있는데 값이 `null` 인 경우(`floodPartLossCnt` 등)는 "정보없음" 으로
구분해서 표시한다 — 이것도 0 으로 바꾸지 않는다.
0 으로 채우면 '정보 없음' 이 '사고 없음' 으로 둔갑한다. 보험이력을 못 받은
매물은 무사고로 치지 않고 보수적으로 할인한 뒤, 리포트에 "실제 사고이력이
있다면 적정가는 더 낮아집니다" 를 표시한다.

`--probe` 의 `[9-1]` 이 record 응답의 전체 필드와 매핑 결과를 보여주므로,
`<-- 응답에 없음` 이 뜬 항목은 실제 키 이름을 알려주면 바로 붙일 수 있다.

### 최초등록일

배터리 보증 8년의 기준일은 연식(`202312`)이 아니라 **최초등록일**이다.
둘은 몇 달씩 차이나고, 실제로 11개월 차이가 배터리 보증 잔여를
66.7% → 54.7% 로 바꾼 사례가 있다. 응답에 최초등록일이 있으면 그것을 쓰고,
없으면 연식으로 계산하되 리포트에 그 사실을 표시한다.

### 성능기록부 HTML 페이지가 주 소스

부위별 랭크가 완전히 구조화된 것은 **별도 HTML 페이지**다. `inspection` API 는
성능기록부의 일부만 주므로 보조로만 쓴다.

```
https://www.encar.com/md/sl/mdsl_regcar.do?method=inspectionViewNew&carid={carid}
```

여기서 읽는 것:

- **수리 부위 + 좌우 위치 + 상태부호 + 랭크**
  `프론트 휀더(우) ⓧ 교환` → 프론트펜더 / 외판 1랭크 / X
- 주행거리 계기상태 (양호/불량) — **불량이면 조작 의심으로 후보 제외**
- 성능점검 시점 주행거리 (매물 표시와 비교해 조작 탐지)
- 차대번호 표기, 튜닝, 특별이력, 용도변경, 리콜 대상/이행
- 사고이력 / 단순수리 플래그
- 자동차 세부상태 (누유·냉각수·변속기·동력전달·조향·제동·전기·연료누출)
- **고전원전기장치 3항목** (충전구 절연 / 구동축전지 격리 / 고전원전기배선)
- 특기사항 및 점검자 의견, 최초등록일, 검사유효기간

**선택 표시 규칙 (페이지 주석에 명시됨).** 이 페이지는 선택지를 양쪽 다
글자로 적어 두고 클래스로만 실제 판정을 표시한다.

```html
<!-- default 항목 선택된 경우 class 'on' 추가
     default 항목 아닌 항목 선택된 경우 class 'active' 추가 -->
<span class="txt_state on">양호</span>   <- 선택됨
<span class="txt_state">불량</span>      <- 선택 안 됨
```

`txt_state` 를 가진 요소 중 `on` 또는 `active` 가 붙은 것이 값이다.
이 규칙이 없으면 굵기·색·태그로 추정하고, 그것도 안 되면 **판정 불가**로
둔다. 텍스트만 읽어 "양호 불량" 을 값으로 삼으면 멀쩡한 차가 전부 불량이
된다.

**세부상태는 rowspan 을 펼쳐 읽는다.** 대분류에 `rowspan` 이 걸리고 그
아래에 하위 항목이 여러 개 붙는 구조라, 대분류 칸 하나만 보면 하위 항목의
불량을 놓친다. rowspan 이 덮는 행 전부를 읽어 **하나라도 불량이면 그 대분류를
불량**으로 본다. `전기` 같은 낱말은 `사용연료: 전기` 처럼 다른 표에도 나오므로
**세부상태 표 안에서만** 찾는다.

**주행거리는 `txt_detail` 에서 읽는다.** 선택지(많음/보통/적음)는 아무것도
선택돼 있지 않고 실제 수치는 `<span class="txt_detail">19,163km</span>` 에 있다.

**리콜은 감점 대상이 아니다.** 대상이어도 이행했으면 문제가 아니고 미이행이면
인수 전 처리하면 되므로 표시만 한다.

**두 가지 표 배치를 모두 읽는다.**

```
(가) 같은 행      <th>라벨</th><td>값</td>
(나) 헤더 + 데이터  <tr><th>사고이력</th><th>단순수리</th></tr>
                  <tr><td>값</td><td>값</td></tr>
```

(나)를 (가)처럼 읽으면 옆 헤더('상태' 등)를 값으로 집는다. 라벨 일치
품질(정확히 같음 > 접두 > 포함)로 후보를 골라 `주행거리` 가
`주행거리 계기상태` 에 먼저 걸리는 것도 막는다.

**수리 부위는 랭크 '블록' 단위로 읽는다.** 랭크가 `<tr>` 이 아니라
`<div>`/`<ul>` 구조여도 찾도록 태그를 가리지 않고, 라벨만 든 요소가 아니라
내용까지 담은 조상까지 올라간다. 부위는 잎 요소만 인정해
`"프론트 휀더(우) 교환 프론트 도어(우) 교환"` 이 통째로 한 부위로 잡히는
것을 막는다.

**확정된 DOM 구조** (브라우저 Elements 탭 실측):

```html
<ul class="list_state uiListLank1">
  <li><strong class="tit_part">프론트 휀더(우)</strong>
      <div class="txt_state"><span class="i1">교환</span></div></li>
</ul>
<ul class="list_state uiListLankB">
  <li><strong class="tit_part">필러 패널 A(우)</strong>
      <div class="txt_state"><span class="i2">판금</span></div></li>
</ul>
<!-- 수리 없으면 --> <li class="uiLankNone">없음</li>
```

부위명은 `strong.tit_part`, 상태는 `div.txt_state span` 의 **한글 텍스트**를
읽는다. 동그라미 기호나 이미지를 찾을 필요가 없다.
`교환`→X, `판금`/`용접`→W, `부식`→C, `흠집`→A, `요철`→U, `손상`→T.
span 의 class(`i1`, `i2` …)도 함께 수집해 매핑을 검증한다.

**이 목록은 자바스크립트가 그린다.** 별도 API 호출은 없고 데이터가 페이지
안에 이미 들어 있다. 그래서 원본 HTML 만으로 충분하다.

1. **`<script>` 안의 부위별 손상표 — 이것이 기본 경로다.**
   서버가 내려주는 원본 HTML 에는 수리 부위가 `<li>` 로 그려져 있지 않다.
   `<ul class="uiListLank1">` 은 빈 틀이고, 자바스크립트가 script 안 데이터를
   읽어 채운다. 실제 구조는 두 덩어리다.

   ```js
   var performanceCheck = {
     dataGroup: [                                   // (가) 모든 부위의 사전
       { code:'004', name:'frontFenderRight', value:'프론트 휀더(우)', lank:'1' },
       { code:'032', name:'pillarPanelFrontRight', value:'필러 패널 A(우)',
         value_old:'필러 패널(앞)(우)', lank:'B' }, ...
     ],
     cacheElement: function(v){
       this.point=['교환','판금/용접','부식','흠집','요철','손상'];  // 상태 코드표
     }
   }
   performanceCheck.init({                          // (나) 이 차의 수리 내역
     data : {"hood":null, "frontFenderRight":["CHANGE"],
             "frontDoorRight":["CHANGE"], "pillarPanelFrontRight":["METAL"], ...}
   });
   ```

   **(가)는 이 차와 무관한 부위 사전이고, (나)가 이 차의 실제 수리 내역이다.**
   `data` 의 값이 `null` 인 부위는 수리 없음이다. 부위 이름과 랭크는
   `dataGroup` 에서 키(`code` 또는 `name`)로 찾아 붙인다.

   > **(가)를 수리 내역으로 읽으면 무사고 차가 전부 수리된 것처럼 보인다.**
   > `dataGroup` 항목에도 `lank` 와 `value` 가 있어서, 그 둘만 보고 고르면
   > 38개 부위 전부가 수리 내역으로 잡힌다. 실제로 그렇게 읽어서 수리 3건인
   > 차가 37건으로 나온 적이 있다. 그래서 파서는 부위 사전으로 판정된 배열을
   > 수리 내역 후보에서 명시적으로 제외한다.

   손상 코드는 `point` 배열 순서와 같고, 앞에 올수록 무겁다
   (`config.DAMAGE_CODE_TEXT`):

   | 코드 | 뜻 | 상태부호 |
   |---|---|---|
   | `CHANGE` | 교환 | X |
   | `METAL` | 판금/용접 | W |
   | `CORROSION` | 부식 | C |
   | `SCRATCH` | 흠집 | A |
   | `HILLS` | 요철 | U |
   | `DAMAGE` | 손상 | T |

   한 부위에 손상이 여러 개면 **무거운 쪽**을 대표 상태로 쓰고 나머지도 함께
   표시한다. 구버전 표기(`["hood_1", ...]`, 숫자 1~5)도 같은 표로 옮긴다
   (`config.DAMAGE_LEGACY_CODES`).

   자바스크립트 리터럴은 키에 따옴표가 없고 작은따옴표를 쓰므로 `json`
   모듈로는 못 읽는다. 전용 파서를 따로 두었다.

   **`data : null` 은 '못 찾음' 이 아니라 '수리 부위 없음' 이다.** 실제로
   무사고 매물은 이 형태로 온다. 둘을 구분하지 않으면 진짜 무사고 차마다
   "JS 렌더링 의심" 경고가 뜬다. 파서는 `init(...)` 인자를 따로 읽어
   `data` 가 `null` 이면 **0건으로 확정**한다.

   그 밖의 안전장치:

   - 손상 코드에 해당하는 부위를 `dataGroup` 에서 못 찾으면 **추측하지 않고
     미분류**로 둔다
   - `initLankFlag` 가 "이 랭크에 수리 있음" 이라는데 우리가 못 읽었으면
     `없음` 이 아니라 **`판정 불가 (수리 있다고 표시됨)`** 으로 남긴다
   - 페이지가 말하는 랭크와 부위별 법정 랭크가 다르면 **무거운 쪽**을 쓰고
     어긋났다는 사실을 리포트에 남긴다 (손상을 축소하지 않기 위해)
   - 상태 코드가 없으면 `불량` 이 아니라 **판정 불가**다

2. 구형 `lank`/`value` 자리번호 레코드 (부위 목록의 자리번호로 참조하는 형태)
3. 렌더된 DOM (`ul.uiListLank*` > `strong.tit_part` + `div.txt_state`) —
   브라우저에서 저장한 HTML 이면 이 경로로 읽힌다
4. 통째로 박힌 JSON (`\uXXXX` 인코딩 포함)
5. 표/텍스트 기반 추정 (구버전 대비)

**성능기록부를 사진으로만 올린 매물이 있다.** 그 페이지에는 표도 script
데이터도 없고 이미지 한 장뿐이다. 파서 고장이 아니므로 그렇게 표시하고,
모든 항목을 **판정 불가**로 둔다. 절대 무사고로 읽지 않는다 — 이런 매물은
성능기록부를 눈으로 직접 확인해야 한다.

```bash
python collect.py --hunt                    # 원본 HTML 안의 숨은 데이터 탐색
python collect.py --try-urls --carid 12345  # 정적 HTML 우회로 탐색
```

`--hunt` 는 상태 코드표(`point`)·부위 사전(`dataGroup`)·부위별 손상표
(`init` 의 `data`)를 실제로 해석해서, **어느 부위에 어떤 손상이 붙어 있는지
키 단위로** 보여준다. `current` / `initLankFlag` / `stats` 가 script 안
어디에서 정의되는지도 위치와 원문까지 찍어 준다. 마지막에 **지금 파서로 무엇이 읽히는지**
그대로 출력하므로 브라우저 화면과 대조만 하면 된다.
`\uXXXX` 도 디코딩해 세므로, 브라우저에서 "교환" 으로 검색해도 안 나오는
이유(인코딩)까지 함께 보인다.

`--try-urls` 는 인쇄용·모바일·ajax 조각 등 정적 HTML 후보를 시험한다.

**`Copy outerHTML` 은 마지막 수단이다.** 데이터가 script 안에 있으므로
보통은 원본 페이지만으로 충분하다. 위 경로가 전부 0건일 때만 브라우저
Elements 탭에서 최상단 `<html>` 우클릭 → `Copy outerHTML` 로 저장한 파일을
`--inspect-page <파일>` 에 넣는다.

**진단이 막히면 마크업을 뽑아 준다.**

```bash
python collect.py --inspect-page                    # 저장된 HTML 분석 + 진단
python collect.py --inspect-page --find 랭크,휀더      # 특정 키워드 마크업만
python collect.py --inspect-page --carid 42586803   # 그 매물 페이지를 새로 받아 분석
```

`--carid` 는 특정 매물의 성능기록부를 새로 받아 분석하고, **보험이력도 같이
받아 대조**한다. 수리 부위가 비었을 때 그게 진짜 무사고인지, 아니면 자바
스크립트로 나중에 채워지는 구조라 안 보이는 것인지 가려내기 위해서다.

```
[랭크가 비어 있음 — 무사고인지 JS 렌더링인지 판별]
    보험이력: 내차 2 건 / 타차 0 건
! 사고 기록이 있는데 랭크 목록이 비었습니다
  -> 자바스크립트로 나중에 채워지는 구조로 보입니다.
! JS 렌더링 의심 클래스 발견: uilistlank, uilanknone
```

JS 렌더링이 의심되면 랭크 목록을 채우는 스크립트 조각을 뽑아 준다.
그 스크립트가 부르는 데이터 API 를 찾으면 HTML 대신 그걸 쓰면 된다.

라벨이 아예 없는 항목(파싱 문제 아님)과 라벨은 있는데 값을 못 읽은 항목
(진짜 문제)을 나눠 보여주고, 후자는 실제 마크업 원문을 출력한다.

> 상태 부호는 동그라미 문자(ⓧ ⓦ ⓒ ⓐ ⓤ ⓣ)를 우선한다. 맨 글자 X/W/C/A/U/T
> 는 `필러 패널 **A**(우)` 처럼 부위 이름의 일부일 수 있어서, 동그라미가
> 하나도 없고 상태를 뜻하는 낱말이 같이 있을 때만 받는다.

| 등급 | 부위 | 감점 |
|---|---|---|
| 외판 1랭크 | 후드, 프론트펜더, 도어, 트렁크리드, 라디에이터서포트 | 0~2 |
| 외판 2랭크 | 쿼터패널, 루프패널, 사이드실패널 | 5~12 |
| 골격 A랭크 | 프론트패널, 크로스멤버, 인사이드패널, 트렁크플로어, 리어패널 | 15~22 |
| 골격 B랭크 | 사이드멤버, 휠하우스, 필러패널(A/B/C), 패키지트레이 | 25~35 |
| 골격 C랭크 | 대시패널, 플로어패널 | 40+ **후보 제외** |
| 전기차 배터리팩 | 고전압 배터리 하부 손상 | 40+ **후보 제외** |

**"무사고" 표기를 그대로 믿지 않는다.** 외판 1랭크 교환은 법적으로 무사고로
표기되므로, 무사고 매물이라도 실제 수리 부위를 표시한다.

### 고전원전기장치 — 전기차 핵심

충전구 절연 / 구동축전지 격리 / 고전원전기배선 3항목을 별도로 읽어 리포트에
강조 표시한다. 불량이면 항목당 **−400만원**(`PRICING["ev_hv_bad_manwon"]`).
점검 결과가 없으면 "정보없음" 으로 표시한다.

### 점검자 코멘트 파싱은 보조 수단

성능기록부 페이지를 못 받았을 때만 쓴다. 코멘트는 딜러 자유 기술이라
페이지가 있으면 그쪽이 우선한다. `repair_grade_source` 컬럼에 어느 쪽을
썼는지 남는다.

구어체 매핑은 `config.COMMENT_PART_ALIASES` 에 있다. 정형 면책문구
("중고차 특성상 부분적인 판금,도색이 있을 수 있습니다")는 걷어내고,
수리 방식이 안 적혀 있으면 **R(방식 미상)** 로 둔다.

### 엔카 옵션은 수집하지 않는다

엔카 옵션 목록에는 에어서스펜션·후륜조향 항목 자체가 없다(옵션 페이지에서
직접 확인). 나머지도 숫자 코드로만 와서 쓸 수 없다. **에어서스·후륜조향을
포함한 옵션 확인은 헤이딜러 숨은이력 전담**이며, 옵션 코드 변환표 탐색은
중단했다.

### 주행거리 조작 탐지

성능점검 응답의 `master.detail.mileage`(점검 시점 주행거리)와 매물 표시
주행거리를 비교한다. 계기판은 되감지 않는 한 늘기만 하고 성능점검은 매물
등록보다 앞서므로, **성능점검 km 가 표시 km 보다 크면 조작을 의심**해야 한다.

- 100km 이하 차이: 표기 반올림으로 보고 무시
- 그 이상: −35점 + 리포트 상단에 굵은 경고
- 5,000km 이상: 후보에서 제외

### 성능점검에서 함께 수집하는 것

`master.detail` 아래에서 침수 여부(`waterlog`), 리콜 이행
(`recall` / `recallFullFillTypes`), 점검자 코멘트(`comments`), 튜닝(`tuning`),
용도 변경(`usageChangeTypes`), 특이사항(`seriousTypes`), 차대번호(`vin`)를
가져온다. `master.accdient` / `master.simpleRepair` 플래그도 함께 본다.

`etcs` 의 **'수리필요'** 항목은 지금 손봐야 하는 부분이라 별도로 표시한다.

`inners` 는 차체 부위가 아니라 자기진단(원동기·변속기 등) 항목이므로
등급 채점에서 빼고 참고 표시만 한다. 부위 등급 대상은 `outers` 와 `etcs` 다.

### 사고 건별 상세

`accidents` 배열의 건별 일자·유형·보험금·부품/공임/도장비를 나열한다.
`type` 코드의 의미는 문서화돼 있지 않아 추정하되, **`myAccidentCnt` /
`otherAccidentCnt` 와 건수를 대조해 자동 검증**한다. 일치하면 그대로,
불일치하면 "추정과 불일치 — 코드 의미 재확인 필요" 로 표시한다.

```
20240301 내차 피해 보험금 2,500,000원 (부품 800,000원, 공임 400,000원, 도장 250,000원)
20230715 타차 가해 보험금 900,000원
```

### 침수·전손·골격C·배터리팩 손상은 제외

감점이 아니라 후보에서 **제외**한다. 순위표에서 빠지고 콘솔에 제외 사유가
출력된다. 시세 회귀 표본으로는 계속 쓰인다.

## 저평가 판정 — 이 도구의 핵심

### 세 가지 자로 잰다

```
절대금액  적정가 - 판매가              실제로 아끼는 돈
비율      (적정가 - 판매가) / 적정가    싼 차일수록 크게 나온다
σ         (적정가 - 판매가) / 시세선 잔차   둘의 왜곡을 걷어낸다
```

절대금액만 보면 비싼 차가 항상 위로 온다 — 2억짜리의 5%는 1,000만원이다.
비율만 보면 싼 차가 항상 위로 온다. **σ 는 시세선 자체의 오차로 나눈 값**
이라 1.9억 M70과 1.1억 xDrive40을 같은 자로 잰다.

| σ | 뜻 |
|---|---|
| \|σ\| < 1 | 시세선 오차 범위 안. 통계적으로 "싸다" 고 말하기 어렵다 |
| \|σ\| > 2 | 우연으로 보기 어렵다. 실제로 확인할 값어치가 있다 |

```bash
python score.py                  # 기본: σ 순
python score.py --sort amount    # 절대금액 순
python score.py --sort pct       # 비율 순
```

### "왜 싼가" — 판정

싼 것만으로는 부족하다. **그럴 만한 이유가 있는지**를 봐야 한다.

적정가는 이미 사고·과주행·배터리·소유이력을 금액으로 깎았다. 그러고도
남은 차액이 진짜 질문 대상이다. 그런데 적정가 식에 **안 들어간** 할인
사유가 따로 있다:

| 사유 | 왜 싼가 |
|---|---|
| 성능기록부가 사진뿐 | 수리 부위·고전원전기장치를 확인할 수 없다 |
| 자차보험 미가입 기간 | 그 기간 사고는 보험 기록에 안 남는다. '무사고' 가 약해진다 |
| 딜러 장기 보유 | 협상 여지이자, 남들이 다 보고 지나쳤다는 신호 |
| 재등록 | 한 번 안 팔려서 다시 올린 매물 |
| 저당 설정 이력 | 소유 관계가 깔끔하지 않다 |
| 사고 부위 미상 | 사고는 있는데 어디를 고쳤는지 모른다 |

이것들을 금액으로 환산해(`config.DISCOUNT_REASONS`) 저평가 폭과 견준다.

```
할인 이유 충분        설명 금액 >= 저평가 폭   진짜 저평가로 보기 어렵다
일부 설명됨           일부만 설명됨            남은 만큼은 확인할 값어치
설명되지 않는 저평가   설명할 사유를 못 찾음     >> 직접 확인할 매물
```

계수는 **보수적으로(=설명을 크게)** 잡았다. 진짜 기회를 놓치는 것보다
가짜 기회에 속는 쪽이 더 비싸기 때문이다.

### 시세선 — 잔존율로 그린다

트림이 섞이면 가격을 직접 회귀할 수 없다. iX 는 xDrive40(신차가 1.1억)
부터 M70(1.9억)까지라 같은 연식·주행거리라도 가격이 두 배 가까이 벌어진다.
그대로 회귀하면 **'비싼 트림' 을 '고평가' 로 읽는다.**

그래서 가격이 아니라 **잔존율**을 회귀한다.

```
잔존율 = a + b×경과연수 + c×(주행거리/1000)
적정가 기준선 = 잔존율 × 그 매물의 신차가
```

트림 차이는 신차가가 흡수하므로 표본을 트림별로 쪼갤 필요가 없다.
희소 트림도 살고, 잔차가 % 단위라 비싼 트림과 싼 트림을 같은 자로 잰다.
신차가(`category.originPrice`)가 없는 매물이 30% 를 넘으면 예전처럼
가격을 직접 회귀하는 방식으로 물러난다(콘솔에 표시됨).

**이상치는 빼되, 영향력만으로 빼지 않는다.** 17만km 매물처럼 x 가 멀리
떨어진 점은 레버리지가 늘 크지만, 그 점이 선 위에 얌전히 있으면 오히려
기울기를 잡아 주는 귀한 표본이다. Cook 거리와 스튜던트화 잔차가 **둘 다**
클 때만 뺀다 — 실제로 잘못 붙은 가격만 걸러낸다.

**차종을 합칠지는 매번 재서 정한다.** 잔존율로 정규화했으니 브랜드가
달라도 원리상 한 줄로 세울 수 있고, 합치면 표본이 배로 늘어난다. 다만
브랜드별 감가 속도가 다르면 합치는 순간 양쪽 다 틀린 선이 된다. 그래서
따로 그린 두 선의 결합 잔차와 합친 선의 잔차를 실제로 견주고, 나빠지지
않을 때만 합친다(`BASELINE["pool_models"] = "auto"`).

**리스·렌트는 표본에만 쓰고 순위에서 뺀다.** 승계 매물의 표시 가격은
차값이 아니라 인수금이라 '살 대상' 으로 같은 자로 잴 수 없다. 시세 표본에
넣을지는 `INCLUDE_LEASE_IN_BASELINE` 로 정하는데, 포함/제외 두 경우의
잔존율과 잔차가 콘솔에 나란히 찍히므로 보고 정하면 된다.

## 반복 실행 — 몇 주에 걸쳐 지켜보기

한 번 찍은 값만으로는 '싸다' 를 말할 수 없다. 같은 매물이 몇 주째 안
팔리는지, 가격이 내렸는지, 시장 전체가 빠지는지를 봐야 판단이 선다.

```
data/history/YYYY-MM-DD/listings.csv   그날 수집분 전체
data/history/YYYY-MM-DD/market.json    그날의 시세선 계수
data/history/index.json                매물별 최초 등장 · 가격 이력
```

매 실행마다 자동으로 쌓인다. 리포트 맨 위에 다음이 나온다:

- **가격이 내린 매물** — 딜러가 값을 내렸다 = 안 팔리고 있다 = 협상 여지
- **새로 올라온 매물**
- **사라진 매물** — 팔렸거나 내렸다. 시장이 얼마나 빨리 도는지 보여준다
- **시세 추이** — 기준점(3년 / 45,000km)에서의 잔존율 변화

기준점을 고정해 비교하는 이유: 주마다 표본의 연식·주행 구성이 달라지므로
계수만 보면 헷갈린다. 한 점을 정해 두고 그 점의 값을 비교해야 시장이
오르는지 내리는지 보인다. **잔존율이 내려가는 중이면** 지금 저평가로
보이는 매물도 몇 주 뒤엔 평범한 가격이 된다.

매물을 잇는 기준은 **차량번호**다. 딜러가 같은 차를 새 매물번호로 다시
올려도 이어서 추적해야 '몇 주째 안 팔리는 차' 가 보인다.

딜러 보유 기간은 엔카의 최초 광고일(`manage.firstAdvertisedDateTime`)을
쓰고, 없으면 이 도구가 처음 본 날로 대신한다. 어느 쪽을 썼는지 표시된다.

## 새 차종 추가하기

`config.py` 의 `TARGETS` 에 dict 를 하나 더 넣으면 끝이다. 시세선·적정가·
저평가 판정·리포트는 전부 자동으로 따라온다.

```python
{
    "key": "model_y",              # 내부 식별자 (영문 소문자·숫자·밑줄)
    "label": "테슬라 Model Y",      # 리포트에 나오는 이름
    "car_type": "N",               # N=수입, Y=국산
    "manufacturer": "테슬라",       # 엔카 표기 그대로
    "model_group": "Model Y",
    "model": None,                 # 세부 모델이 필요할 때만
    "confirmed": False,            # --probe 로 확인하기 전까지 False
    "badge_contains": [],          # 트림 필터 (비우면 전부)
    "badge_excludes": [],
    "year_from": 2021,
    "year_to": 2026,
    "airsus_keywords": [],
}
```

**값을 추측하지 말고 실제로 물어본다.** 표기가 한 글자만 달라도 0건이 나온다.

```bash
python collect.py --discover                              # 제조사 목록
python collect.py --discover --mfr 테슬라                   # 그 제조사의 모델그룹
python collect.py --discover --mfr 테슬라 --mg "Model Y"    # 하위 모델
python collect.py --probe                                 # 지금 설정이 실제로 먹는지
```

실제로 벤츠 EQE 는 `ModelGroup=EQE` 만으로는 세단(V295)과 SUV 가 섞여서,
`Model="EQE SUV X294"` 까지 내려가야 SUV 만 걸러졌다. `--discover` 없이
`"EQE SUV"` 로 적었을 때는 **0건**이 나왔다.

**트림은 대개 좁히지 않는 편이 낫다.** 잔존율 회귀가 신차가로 트림 차이를
흡수하므로, 넓게 받을수록 표본이 늘어 시세선이 정확해진다.

새 차종을 넣은 뒤에는 반드시 `--probe` 로 0건이 아닌지 확인할 것.
0건이면 대개 `model_group` 표기나 `car_type` 이 틀린 것이다.

배터리 보증(`BATTERY_WARRANTY`)은 현재 8년/16만km 고정이다. 보증 조건이
다른 차종을 넣으면 이 값도 확인해야 한다.

## 3단계 — 헤이딜러 숨은이력 병합 (`merge.py`)

외부 OCR·비전 API를 쓰지 않는다. 이미지 판독은 **클로드 코드가 세션 안에서
직접** 수행하므로 추가 비용이 없다.

```bash
# 1) 조회할 차량번호 목록
python merge.py --list

# 2) 헤이딜러 앱 '숨은이력찾기'에서 각 번호를 수동 조회하고
#    결과 화면 스크린샷을 hidden/ 에 저장
#    파일명에 차량번호를 넣으면 자동 매칭된다: hidden/112다2644.png

# 3) 이미지 목록과 판독 요청문 출력
python merge.py --show

#    → 이 출력을 클로드 코드에 주면 클로드가 이미지를 읽어
#      hidden/extracted.json 을 생성한다

# 4) 병합 + 최종 점수 재계산 + 리포트
python merge.py --apply
```

`hidden/extracted.json` 형식 (`hidden/extracted.template.json` 참고):

```json
{
  "records": [
    {
      "plate_no": "112다2644",
      "source_image": "hidden/112다2644.png",
      "battery_maker": "삼성SDI",
      "airsus": true,
      "insurance_repair_won": 0,
      "insurance_summary": "내차 0건 / 상대차 0건",
      "notes": "출고옵션에 에어서스펜션 포함 확인"
    }
  ]
}
```

`airsus` 는 `true` / `false` / `null`(화면에서 판단 불가) 세 가지를 구분한다.

**재계산 가감점** (`config.py`) — 여기가 실질적인 판정 단계다.
출고 기록에 근거한 확정 정보이고 차량 가치에 미치는 영향이 크므로,
1차 점수를 뒤집을 만큼 크게 반영한다.

| 항목 | 조정 |
|---|---|
| 배터리 삼성SDI | **+15** |
| 배터리 LG·SK온 | +5 |
| 배터리 CATL | 0 |
| 배터리 파라시스 | **−40** |
| 에어서스 장착 확정 | **+20** |
| 에어서스 미장착 확정 | **−12** |
| 보험 수리이력 | 0원 +5 / ~50만 −2 / ~200만 −6 / ~500만 −14 / 500만 초과 −25 |

실제로 1차 1위였던 매물이 파라시스 + 에어서스 미장착 + 380만원 수리이력으로
확인되자 29대 중 28위로 내려간 사례가 있다. 반대로 1차 3위가 삼성SDI +
에어서스 장착으로 1위가 되었다. **1차 순위는 헤이딜러 조회 대상을 고르는
용도이지 결론이 아니다.**

숨은이력을 조회하지 않은 매물은 해당 항목이 미반영 상태이므로 같은 기준으로
비교되지 않는다. 리포트에 그 사실을 표시한다.

## 주의

- 개인 검토용 **소량 수집** 전용이다. 요청 간격을 줄이거나 병렬화하지 말 것.
- 차단이 감지되면 즉시 멈춘다. 우회를 시도하지 않는다.
- 점수는 공개 매물 정보에 기반한 **상대 비교**일 뿐 차량의 실제 상태를
  보증하지 않는다. 계약 전 리포트의 체크리스트를 직접 확인할 것.
- `hidden/` 의 스크린샷과 `data/` 산출물은 개인 차량 정보이므로
  `.gitignore` 로 제외되어 있다.
