# car-hunter

엔카(encar.com) 중고 전기차 매물을 수집해 가성비 점수를 매기고,
헤이딜러 '숨은이력찾기' 결과를 병합해 최종 순위 리포트를 만드는 개인 검토용 도구.

**대상 차종**
- BMW iX xDrive50 (2022~2024년식)
- 벤츠 EQE SUV 350 4MATIC (2023~2024년식)

대상 차종·연식·점수 가중치는 전부 `config.py` 에서 바꾼다.

## 데이터 소스의 역할 분담

| 소스 | 담당 | 신뢰도 |
|---|---|---|
| **엔카** | 가격, 연식, 주행거리, 지역, 신차가, 사고 유무, 엔카진단, 소유자 변경 | 객관적 |
| **헤이딜러 숨은이력** | 에어서스 장착, 배터리 제조사, 보험 수리이력 | 출고 기록 기반 |
| ~~엔카 옵션 목록·판매자 설명~~ | **점수에 쓰지 않음** | 딜러 작성 문구 |

엔카의 옵션 목록과 판매자 설명글은 딜러가 홍보용으로 쓴 자유 텍스트다.
없는데 적어두거나 있는데 안 적는 경우가 흔하다. 실제 검증에서 옵션 코드에
없어 "에어서스 미장착" 으로 본 매물의 판매자 설명에 "에어서스펜션, 후륜조향
옵션적용차량" 이 적혀 있었다. 그래서 **에어서스와 배터리 제조사는 1차
점수에 넣지 않고, 3단계 헤이딜러 출고 기록에서 확정한다.** 엔카 쪽 언급
여부는 참고 표시로만 남는다.

## 설치

```bash
pip install -r requirements.txt
```

## 전체 흐름

```
collect.py  ─→  data/listings.csv , data/details.json
score.py    ─→  data/scored.csv  , report.html (1차)
                  ↓  상위 10대 차량번호를 헤이딜러 앱에서 수동 조회
                  ↓  결과 스크린샷을 hidden/ 에 저장
merge.py    ─→  data/merged.csv  , report.html (최종)
```

세 단계는 서로 독립적으로 실행할 수 있다. 각 단계는 파일로만 소통한다.

## 1단계 — 수집 (`collect.py`)

**파서를 믿기 전에 실제 응답부터 확인할 것.**

```bash
python collect.py --probe
```

`--probe` 는 11가지를 실제로 두들겨 보고 결과를 보고한다:

1. `/premium` · `/general` 중 어느 엔드포인트가 살아 있는지
2. 실제 요청 URL (브라우저 주소창에 붙여넣어 대조 가능)
3. 응답 최상위 구조
4. 결과 1건의 전체 필드
5. 필드 매핑 결과 — 실패한 필드에 `<-- 매핑 실패` 표시
   (`trim_detail` 처럼 없어도 정상인 항목은 `(선택 항목)` 으로 구분)
6. **어떤 조건이 매물을 걸러내는지** — 연식 / Hidden / CarType / AdType /
   하위 Model 을 하나씩 빼며 총건수를 비교하고, `CarType` 반대값도 시험한다
7. **연식 필터가 실제로 먹는지** (필터 유/무 총건수와 반환 연식 범위 비교)
8. **페이징이 실제로 먹는지** (1·2페이지 ID 중복 여부)
9. 첫 매물의 **상세 API 4종** (차량번호/옵션, 사고이력, 성능점검, 엔카진단)
10. **옵션 배열 탐색** — 상세 응답 안의 모든 배열을 경로·길이·타입·샘플과
    함께 나열하고, 옵션명 배열 / 옵션 코드 배열 / 코드→이름 변환표를 구분해
    표시한다. 상세 응답 전체는 `data/raw_detail.json` 에 저장된다
11. 최종 파싱 결과 (차량번호, 옵션 수, 에어서스 판별 상태 등)

### 시도했다가 폐기한 방법

`options.etc` 에 딜러가 한글로 적어 둔 항목을 정답 라벨 삼아 옵션 코드의
정체를 역추적하는 스크립트를 만들었으나 **실전에서 틀렸다.** 라벨 자체가
딜러 자유 기술이라 정답이 될 수 없었고, 양성 표본도 1대뿐이라 통계적
근거가 없었다. `samples/experimental_infer_options.py` 에 기록으로만 남겼다.
사용하지 말 것.

## 2단계 — 가성비 스코어링 (`score.py`)

```bash
python score.py            # 기본 상위 10대
python score.py --top 15
```

점수 구성 (`config.SCORING`) — **엔카의 객관적 데이터만** 사용:

| 항목 | 배점 | 산출 |
|---|---|---|
| 시세 잔차 | 0~40 | 모델별 `가격 ~ (경과연수, 주행거리)` 회귀의 예측가 대비 저평가 정도 |
| 배터리 보증 잔여 | 0~20 | **최초등록일** 기준 8년 / 16만km 중 먼저 도달하는 쪽의 잔여 비율 |
| 신차가 대비 감가율 | 0~10 | `originPrice` 대비 감가. 모델이 다른 매물을 한 줄로 세울 때 의미가 있다 |
| 가점 | + | 무사고 +8(보험이력으로 확인된 경우만) · 엔카진단 +5 · 1인소유 +4 |

감점 — 차 상태를 가격에 반영하기 위한 부분:

| 항목 | 감점 |
|---|---|
| 사고 내차 피해 | 건당 4 |
| 사고 타차 가해 | 건당 1.5 |
| 내차 수리비 규모 | ~50만 2 / ~200만 6 / ~500만 14 / 500만 초과 25 |
| **골격·판금 수리** | **18** (사이드멤버·필러·대시패널·플로어 등) |
| 단순 교환 | 3 (범퍼·펜더·도어 등 볼트온) |
| **과거 대여·영업·관용 등록** | **15** (현재 판매형태와 별개) |
| 과주행 | 연 2.5만km 초과 6 / 3만km 초과 12 |
| 침수·전손 | 40 |
| 현재 렌트·리스 매물 | 10 |
| 보험이력 미확보 | 3 (정보 부재 자체가 위험) |

### 없는 값은 0 으로 채우지 않는다

응답에 없는 필드는 빈 값으로 두고 리포트에 "응답에 없음" 으로 표시한다.
키는 있는데 값이 `null` 인 경우(`floodPartLossCnt` 등)는 "정보없음" 으로
구분해서 표시한다 — 이것도 0 으로 바꾸지 않는다.
0 으로 채우면 '정보 없음' 이 '사고 없음' 으로 둔갑한다. 특히 보험이력을
못 받은 매물에는 무사고 가점을 주지 않고 오히려 소폭 감점한다.

`--probe` 의 `[9-1]` 이 record 응답의 전체 필드와 매핑 결과를 보여주므로,
`<-- 응답에 없음` 이 뜬 항목은 실제 키 이름을 알려주면 바로 붙일 수 있다.

### 최초등록일

배터리 보증 8년의 기준일은 연식(`202312`)이 아니라 **최초등록일**이다.
둘은 몇 달씩 차이나고, 실제로 11개월 차이가 배터리 보증 잔여를
66.7% → 54.7% 로 바꾼 사례가 있다. 응답에 최초등록일이 있으면 그것을 쓰고,
없으면 연식으로 계산하되 리포트에 그 사실을 표시한다.

### 성능점검 — 수리 부위 법정 등급

성능점검은 `https://api.encar.com/v1/readside/inspection/vehicle/{id}` 에서 온다(확인됨).
누유·부식·타이어 상태와 함께, 수리 부위를 **한국 성능점검기록부 법정 분류**로
등급화해 감점을 차등한다 (`config.INSPECTION_RANKS`).

| 등급 | 부위 | 감점 |
|---|---|---|
| 외판 1랭크 | 후드, 프론트펜더, 도어, 트렁크리드, 라디에이터서포트 | 0~2 |
| 외판 2랭크 | 쿼터패널, 루프패널, 사이드실패널 | 5~12 |
| 골격 A랭크 | 프론트패널, 크로스멤버, 인사이드패널, 트렁크플로어, 리어패널 | 15~22 |
| 골격 B랭크 | 사이드멤버, 휠하우스, 필러패널(A/B/C), 패키지트레이 | 25~35 |
| 골격 C랭크 | 대시패널, 플로어패널 | 40+ **후보 제외** |
| 전기차 배터리팩 | 고전압 배터리 하부 손상 | 40+ **후보 제외** |

※ 범퍼는 성능점검 대상이 아니라 기록에 나오지 않는다(단순수리 취급).

상태 부호 `X`(교환) `W`(판금/용접) `C`(부식) `T`(손상) `U`(요철) `A`(흠집)를
파싱해, 같은 부위라도 교환과 판금을 구분한다. 감점은 등급 범위 안에서
부호별 가중치로 정해진다 — 예: 사이드멤버 `W` → 25 + (35−25)×0.75 = **32.5**.

부위가 여러 곳이면 가장 심한 곳을 기준으로 하고 나머지는 30%만 더한다.
경미한 외판 수리 여러 건이 골격 수리 한 건보다 커지는 왜곡을 막기 위해서다.

**"무사고" 표기를 그대로 믿지 않는다.** 외판 1랭크 교환은 법적으로 무사고로
표기되므로, 무사고 매물이라도 실제 수리 부위를 리포트에 표시한다:

```
트렁크리드 교환(X) — 외판 1랭크, 구조 영향 없음
사이드멤버 판금/용접(W) — 골격 B랭크, 충돌이 뼈대까지 전달됨
```

등급표에 없는 부위명이 나오면 **미분류**로 표시하고 경고한다. `--probe` 의
`[9-2]` 가 그 이름을 알려주므로 등급표에 추가하면 된다.

### 주행거리 조작 탐지

성능점검 응답의 `master.detail.mileage`(점검 시점 주행거리)와 매물 표시
주행거리를 비교한다. 계기판은 되감지 않는 한 늘기만 하고 성능점검은 매물
등록보다 앞서므로, **성능점검 km 가 표시 km 보다 크면 조작을 의심**해야 한다.

- 100km 이하 차이: 표기 반올림으로 보고 무시
- 그 이상: −35점 + 리포트 상단에 굵은 경고
- 5,000km 이상: 후보에서 제외

### 성능점검에서 함께 수집하는 것

`master.detail` 아래에서 침수 여부(`waterlog`), 리콜 이행
(`recall` / `recallFullFillTypes`), 점검자 코멘트(`comments`), 튜닝(`tuning`),
용도 변경(`usageChangeTypes`), 특이사항(`seriousTypes`), 차대번호(`vin`)를
가져온다. `master.accdient` / `master.simpleRepair` 플래그도 함께 본다.

`etcs` 의 **'수리필요'** 항목은 지금 손봐야 하는 부분이라 별도로 표시한다.

`inners` 는 차체 부위가 아니라 자기진단(원동기·변속기 등) 항목이므로
등급 채점에서 빼고 참고 표시만 한다. 부위 등급 대상은 `outers` 와 `etcs` 다.

### 사고 건별 상세

`accidents` 배열의 건별 일자·유형·보험금·부품/공임/도장비를 나열한다.
`type` 코드의 의미는 문서화돼 있지 않아 추정하되, **`myAccidentCnt` /
`otherAccidentCnt` 와 건수를 대조해 자동 검증**한다. 일치하면 그대로,
불일치하면 "추정과 불일치 — 코드 의미 재확인 필요" 로 표시한다.

```
20240301 내차 피해 보험금 2,500,000원 (부품 800,000원, 공임 400,000원, 도장 250,000원)
20230715 타차 가해 보험금 900,000원
```

### 침수·전손·골격C·배터리팩 손상은 제외

감점이 아니라 후보에서 **제외**한다. 순위표에서 빠지고 콘솔에 제외 사유가
출력된다. 시세 회귀 표본으로는 계속 쓰인다.

## 3단계 — 헤이딜러 숨은이력 병합 (`merge.py`)

외부 OCR·비전 API를 쓰지 않는다. 이미지 판독은 **클로드 코드가 세션 안에서
직접** 수행하므로 추가 비용이 없다.

```bash
# 1) 조회할 차량번호 목록
python merge.py --list

# 2) 헤이딜러 앱 '숨은이력찾기'에서 각 번호를 수동 조회하고
#    결과 화면 스크린샷을 hidden/ 에 저장
#    파일명에 차량번호를 넣으면 자동 매칭된다: hidden/112다2644.png

# 3) 이미지 목록과 판독 요청문 출력
python merge.py --show

#    → 이 출력을 클로드 코드에 주면 클로드가 이미지를 읽어
#      hidden/extracted.json 을 생성한다

# 4) 병합 + 최종 점수 재계산 + 리포트
python merge.py --apply
```

`hidden/extracted.json` 형식 (`hidden/extracted.template.json` 참고):

```json
{
  "records": [
    {
      "plate_no": "112다2644",
      "source_image": "hidden/112다2644.png",
      "battery_maker": "삼성SDI",
      "airsus": true,
      "insurance_repair_won": 0,
      "insurance_summary": "내차 0건 / 상대차 0건",
      "notes": "출고옵션에 에어서스펜션 포함 확인"
    }
  ]
}
```

`airsus` 는 `true` / `false` / `null`(화면에서 판단 불가) 세 가지를 구분한다.

**재계산 가감점** (`config.py`) — 여기가 실질적인 판정 단계다.
출고 기록에 근거한 확정 정보이고 차량 가치에 미치는 영향이 크므로,
1차 점수를 뒤집을 만큼 크게 반영한다.

| 항목 | 조정 |
|---|---|
| 배터리 삼성SDI | **+15** |
| 배터리 LG·SK온 | +5 |
| 배터리 CATL | 0 |
| 배터리 파라시스 | **−40** |
| 에어서스 장착 확정 | **+20** |
| 에어서스 미장착 확정 | **−12** |
| 보험 수리이력 | 0원 +5 / ~50만 −2 / ~200만 −6 / ~500만 −14 / 500만 초과 −25 |

실제로 1차 1위였던 매물이 파라시스 + 에어서스 미장착 + 380만원 수리이력으로
확인되자 29대 중 28위로 내려간 사례가 있다. 반대로 1차 3위가 삼성SDI +
에어서스 장착으로 1위가 되었다. **1차 순위는 헤이딜러 조회 대상을 고르는
용도이지 결론이 아니다.**

숨은이력을 조회하지 않은 매물은 해당 항목이 미반영 상태이므로 같은 기준으로
비교되지 않는다. 리포트에 그 사실을 표시한다.

## 최종 출력 — `report.html`

외부 CDN 없이 자체 완결된 단일 HTML (인라인 SVG 차트, 다크모드 대응).

- 모델별 시세 분포 산점도 + 회귀 시세선 (파랑=저평가, 빨강=고평가)
- 최종 순위표: 차량번호 강조, 가격 vs 예측가, 연평균 주행, 배터리 보증 잔여,
  매물·사진 링크, 매물별 추천/주의 사유
- **계약 전 수동 확인 항목** 체크리스트 (SOH 진단, 에어서스 실차 확인, 하부 점검 등)

## 파일 구성

| 파일 | 역할 |
|---|---|
| `config.py` | 대상 차종, 요청 정책, 점수 가중치 — 튜닝은 여기서만 |
| `common.py` | 경로·로깅·CSV/JSON·숫자/날짜 유틸 |
| `encar_api.py` | 엔카 엔드포인트, 방어적 파서, 차단 감지 |
| `collect.py` | 1단계 |
| `scoring.py` | 점수 계산 코어 (2·3단계 공용) |
| `score.py` | 2단계 |
| `merge.py` | 3단계 |
| `report.py` | report.html 생성 |
| `infer_options.py` | 옵션 코드 정체 역추적 |
| `samples/` | 오프라인 점검용 합성 데이터 생성기 |

## 주의

- 개인 검토용 **소량 수집** 전용이다. 요청 간격을 줄이거나 병렬화하지 말 것.
- 차단이 감지되면 즉시 멈춘다. 우회를 시도하지 않는다.
- 점수는 공개 매물 정보에 기반한 **상대 비교**일 뿐 차량의 실제 상태를
  보증하지 않는다. 계약 전 리포트의 체크리스트를 직접 확인할 것.
- `hidden/` 의 스크린샷과 `data/` 산출물은 개인 차량 정보이므로
  `.gitignore` 로 제외되어 있다.
